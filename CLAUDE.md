# Wiffle Ball Broadcast Overlay — Claude Context

## What this is
A live broadcast overlay system for a small wiffle ball league. Runs as a single Vite + React + TypeScript app with three routes served to different devices simultaneously. Firebase Realtime Database is the **only** communication channel between routes — there are no direct API calls between views.

## Stack
- **Vite + React + TypeScript** — build tool and framework
- **Firebase Realtime Database** (SDK v10) — sole source of truth; all state lives here
- **Tailwind CSS v4** with `@tailwindcss/vite` plugin — utility classes
- **Framer Motion** — overlay animations
- **React Router v6** — three routes
- **Google Fonts** — Barlow Condensed (scoreboard numbers/labels) + DM Sans (UI text)

## Routes

| Route | Device | Purpose |
|---|---|---|
| `/overlay` | OBS browser source (1920×1080) | On-screen graphics — read-only, never writes Firebase |
| `/controller` | Tablet or desktop browser | Producer control panel — the only writer; responsive layout |
| `/scorekeeper` | Phone or tablet | Per at-bat logging (stretch goal, writes `/gameStats`); responsive layout |

## Firebase data shape
```
/game/meta                         — GameMeta: scores, inning, outs, bases, team IDs
/game/matchup                      — MatchupState: { batterId, pitcherId, lastPitcherHome, lastPitcherAway }
/teams/{teamId}                    — Team: name, shortName, primaryColor, secondaryColor, logoUrl
/overlay                           — activeScene + statOverlay + timer + scoreboardBorder + scoreboardScale
/overlay/timer                     — TimerState: { durationMs, startedAt, running } — default 60 min
/players/{id}                      — Player: name, teamId, position, stats: { hitting?: HittingStats, pitching?: PitchingStats }
/games/{gameId}                    — GameRecord: teams, date, inning, outs, scores, finalized, lineups, lineupPosition, matchup
/games/{gameId}/matchup            — { pitcherId, batterId, lastPitcherHome, lastPitcherAway } — persists pitcher across refresh
/games/{gameId}/lineups/{teamId}   — GameLineup (ordered LineupEntry[])
/games/{gameId}/lineupPosition/{teamId} — current batting order index (int)
/gameStats/{gameId}/{atBatId}      — AtBatRecord: full at-bat log entry
/liveRunners/{gameId}              — RunnersState: { first, second, third } — current base state
```
Full type definitions in `src/types.ts`.

## Key architectural decisions (do not reverse without discussion)
- **Overlay is purely reactive** — `OverlayRoute` never writes to Firebase. Only `ControllerRoute` writes.
- **Firebase listeners only** — no Redux, Zustand, or other state lib. Hooks in `src/hooks/` each own one Firebase path.
- **Team colors via CSS custom properties** — `TeamColorInjector` sets `--team-home-primary` etc. on `:root`. All components reference these vars. Do not hardcode team colors in components.
- **Scene system is a flat map** — adding a scene means: new file in `src/scenes/`, export in `src/scenes/index.ts`, render case in `OverlayRoute.tsx`, button in `SCENES[]` in `ControllerRoute.tsx`, type added to `SceneName` in `types.ts`.
- **Auto-dismiss lives in the controller, overlay is read-only** — `/overlay` never writes to Firebase (rules enforce this — only `scorer`/`admin` can write). When the controller writes `overlay/statOverlay.visible = true` or `overlay/homerun.active = true`, it also schedules a `setTimeout` (`scheduleStatDismiss` / `scheduleHomerunDismiss` in `ControllerRoute.tsx`) that writes the flag back to `false` after the intended duration. Stat dismiss uses `dismissDelay` state (20s default, controller-configurable); homerun dismiss is fixed at 10s. Regression: if the controller tab reloads mid-display, the pending timer is lost and the graphic stays up until manually dismissed. Do NOT add Firebase writes to any `/overlay`-rendered component — they will be rejected at the rules layer.
- **`dismissAfterMs` is stored in Firebase** so it's live-adjustable from the controller without a redeploy.
- **Scoreboard is a pill layout** — `Scoreboard.tsx` builds the layout directly (does not use `TeamBug`). Away team: left pill `[NAME | SCORE]` rounded-left, home team: right pill `[SCORE | NAME]` rounded-right, scores facing the center. `TeamBug` still exists for potential future use and accepts a `mirrored` prop, but is not used in the overlay scoreboard.
- **Broadcast scoreboard is centered at 36% width** — `GameScene` wraps `Scoreboard` in a centered container (`width: 36%`). Do not make it full-width or reduce below ~30% or the pills will clip.
- **Scoreboard center section uses fixed-width cells** — inning, bases, and outs each use `width: 150, flexShrink: 0`. Do not use `flex-1` or `justify-center` with gaps — auto-sizing produces unequal cells and off-centers the timer notch.
- **Timer is a notch below the center pill** — the countdown renders in an absolutely-positioned element below the center strip (`top: '100%'`), same `rgba(0,0,0,0.82)` background, rounded bottom corners. It is always visible (displays `0:00` when expired). The controller timer control is a single row: `[min input] [Set] [countdown display] [Start/Pause] [Reset]`.
- **Inning control is two half-inning step buttons** — `InteractiveScoreboard` exposes `onAdvanceHalfInning` and `onRewindHalfInning`. Both clear outs and bases. There are no separate +1/-1 inning or top/bottom toggle buttons.
- **Tailwind v4 cascade layers** — do not add unlayered CSS rules (e.g. `* { padding: 0 }`) after `@import "tailwindcss"` in `index.css`. Unlayered styles outrank Tailwind's `@layer utilities`, silently breaking utility classes. Tailwind's Preflight already handles box-model resets.
- **Controller game-state controls are in `InteractiveScoreboard`** — score, inning, bases, and outs are all controlled via the visual `InteractiveScoreboard` component, not separate button sections. Inning ▲/▼ uses the same symbol as the broadcast overlay.
- **Player stats are nested** — `Player.stats` has two optional buckets: `stats.hitting` (`HittingStats`) and `stats.pitching` (`PitchingStats`). A player can have one or both. Never read flat `stats.avg` etc. — always go through the bucket.
- **Matchup state lives at `/game/matchup`** — `{ batterId, pitcherId, lastPitcherHome, lastPitcherAway }`. `useMatchup` hook owns this path. The controller writes it; the overlay reads it. `lastPitcherHome/Away` are used by `advanceHalfInning` to restore the correct pitcher when the half-inning flips.
- **Batter/pitcher notches on the scorebug** — `Scoreboard.tsx` renders a `PlayerNotch` (Framer Motion spring-bounce) below each team pill. Batter notch shows under the batting team, pitcher notch under the fielding team. Batter notch is hidden while `statOverlayVisible` is true. Both show last name only.
- **Batter auto-clears on play result** — `ControllerRoute` has a `useEffect` that writes `batterId: null` to `/game/matchup` whenever `game.outs` or any base changes. A `mountedRef` guard prevents firing on initial load.
- **Controller "At Bat" section is the single source of truth for who is up** — one unified section handles: batter dropdown (auto-triggers 20s stat overlay on select), HOME RUN button (uses selected batter, auto-scores bases), pitcher dropdown, delay picker, Batter Stats / Pitcher Stats / Dismiss buttons. There are no separate Matchup / Home Run / Stat Overlay sections.
- **`scoreboardBorder` and `scoreboardScale`** live in `/overlay` and are exposed as dev controls in the controller (border toggle, size slider). `showBorder` prop on `Scoreboard` gates the `-webkit-text-stroke`.

## Scorekeeper architecture (ScorekeeperRoute.tsx)
- **Event-sourced scoring** — all game state is derivable by replaying `gameStats/{gameId}`. `liveRunners` and score totals in `games/{gameId}` are derived/cached values, not the source of truth.
- **Active `AtBatResult` types** — the only selectable options are: `single | double | triple | home_run | walk | strikeout | strikeout_looking | groundout | popout`. Legacy values (`flyout | hbp | sacrifice_fly | sacrifice_bunt | fielders_choice | pitchers_poison`) are kept in the type union only so historical records still deserialize correctly — they are not selectable.
- **`groundout` = "Ground / Tag Out"** — any out where the ball was fielded (grounder, tag play). `popout` = ball caught in the air. These are the only two out types.
- **Connected chain rule (groundout only)** — on a `groundout`, if runners occupy consecutive bases starting from 1st (no gap), the lead runner of that chain leaves the basepath (`'sits'`), and the batter stays on 1st. 1 out total. `popout` is explicitly exempt — runners may tag up freely. The rule does NOT apply to `popout`.
- **`'sits'` runner outcome** — distinct from `'out'`. Means the runner leaves the bases as a chain rule consequence (not a genuine out on them). Counts toward `outsOnPlay` the same as `'out'`, but the batter is recorded as the out and the runner is just displaced. Displayed in yellow in the UI.
- **`outsOnPlay`** — `(batterAdvancedTo === 'out' ? 1 : 0) + runners.filter(o => o === 'out' || o === 'sits').length`. Can be 0 for hits/walks, 1 for normal outs, 2+ for double plays.
- **Outs are NOT reset to 0 in `submit()`** — `games/{gameId}/outs` can reach 3+ after the third out. `advanceHalfInning()` is the only function that resets outs to 0. On page refresh with `outs >= 3`, a `useEffect` detects this and restores the `inning_end` interstitial.
- **Pitcher state persistence** — three layers: (1) `advanceHalfInning` calls `setPitcherId(nextPitcherId)` before clearing it; (2) on load a `useEffect` re-hydrates `pitcherId` from `game.matchup.pitcherId` if local state is empty; (3) `inning_end` step pre-fills `nextPitcherId` from `lastPitcherHome`/`lastPitcherAway` based on which side just finished.
- **`lastPitcherHome` / `lastPitcherAway`** in `games/{gameId}/matchup` — store the most recent pitcher selected for each side. Written by `advanceHalfInning` using the INCOMING pitcher: top just ended → away pitches next → `lastPitcherAway`; bottom just ended → home pitches next → `lastPitcherHome`. Pre-fill at `inning_end` uses: `isTopInning ? lastPitcherAway : lastPitcherHome`.
- **Undo** — visible when at batter step with prior at-bat. Calls `undoLastAtBat()` which pre-fills wizard with the last at-bat, then deletes it.
- **Any at-bat is editable or deletable** — the play-by-play log shows every at-bat (current or past innings) as a clickable row. Tapping opens `AtBatEditModal`, which shows a cascade preview (home/away delta + current half outs delta + warnings) before committing. `deleteAtBat` and `applyRecompute` both funnel through `recomputeGameState` (in `scoring/engine.ts`), which replays every half-inning from scratch — migrating runner outcomes by runner ID so that runner intent survives upstream edits — and returns new scores, current-half runners/outs, and warnings. `applyRecompute` writes the recomputed at-bats, score, outs, runners, and both teams' `lineupPosition` in one atomic update, and flips the wizard step between `batter` and `inning_end` if outs crossed the 3-out threshold in either direction.
- **`isSub` is a stat-exclusion tag only** — a sub is a body filling a roster slot for the day; they bat in the batting order exactly like a regular, advance the lineup pointer like a regular, and their at-bats are stored in `gameStats/{gameId}` forever. The only effect of `isSub: true` is at finalization: `computeFinalization` skips sub at-bats when rolling up season totals, but `computeGameSummaries` includes them in the per-game box score. `isSub` is denormalized onto each `AtBatRecord` at submit time from the `LineupEntry.isSub` flag. Custom subs (people not on the roster) are stored in the lineup with a fabricated `sub_<timestamp>` playerId and a `subName` — on the scorebug notch, custom subs' batter preview clears to `null` rather than showing a bogus ID.
- **`lineupPosition` is derived, not counted** — `computeLineupPosition` walks backward through the at-bat log for a team, finds the most-recent batter still present in the current lineup (regulars and subs alike), and returns the slot after them. This self-heals scorer overrides (picked out-of-order batter), mid-game removals, and reorders. Called from `applyRecompute` (on any edit/delete) and `LineupEditScreen.save()` (on lineup edit); `submit()` also advances the pointer directly from the actual batter's slot so the pre-fill is correct on the very next at-bat.
- **Live game stats** — collapsible "Game Stats" panel shows AB/H/RBI/HR/O per batter in a two-column away|home table. "O" (outs) uses result-based check: `['strikeout', 'strikeout_looking', 'groundout', 'popout', 'flyout', 'sacrifice_fly', 'sacrifice_bunt'].includes(result)`.
- **`scoring/engine.ts`** — pure functions, no Firebase/React. `applyAtBat` → narrated log + next runner state. `replayHalfInning` → replays ordered at-bat list. `computeGameStats` → per-player hitting/pitching stats from a list of at-bats. `mergeHittingStats` → merges season totals with a game's stats; OBP uses PA as denominator (`(h + bb) / pa`) since HBP/SF aren't separately tracked in stored season stats.

## Home Run Derby page (DerbyRoute.tsx)
- **`/derby` is a public web page** (like `/stats`), not an overlay — annual 50/50 charity event ($10/entry, half the pot to the winner, half to the Valley Impact Project). A derby *overlay* scene is a separate future project.
- **Entries are submitted via Venmo** (`@emvee311` — `VENMO_HANDLE` constant) — a bold CTA banner at the top tells people to send $10 with note "First Last <HR guess>" (e.g. "Mike Verteramo 25"); admins then record the entry via admin mode. There is no public entry form.
- **The page renders stand-alone** — no `AppNav` header on the page itself and no links out to other routes, but it IS listed in `AppNav`'s links (public "Derby" item) so it's reachable from the main/stats page.
- **`totalHr` means the derby WINNER's personal HR total across all 3 rounds** — not a derby-wide total. Both the entry guess and the posted result use this meaning.
- **Data lives at `/derby`** — `entries/{entryId}` (`DerbyEntry`: name, playerId, totalHr, paid, createdAt) and `result` (`DerbyResult`: winnerPlayerId, totalHr, finalized). `useDerby` hook owns the path.
- **`/derby` is publicly writable at the rules layer** — intentional. Admin mode is a front-end plain-text gate only: a small "Admin" link in the footer (next to the Home Run Derby text) opens a plain password prompt (`ADMIN_PASSWORD` constant at the top of `DerbyRoute.tsx`), state kept in sessionStorage. It is NOT the real `AuthGate` login. Accepted risk: worst case someone edits derby entries.
- **Winner logic** — eligible entries are paid + picked `result.winnerPlayerId`; among those, minimum `|totalHr - result.totalHr|` wins (ties all highlighted). If no eligible entry, banner says the full pot goes to charity.
- **Admin writes are server-confirmed, not trusted from local echo** — the RTDB SDK applies writes to the local cache instantly (latency compensation), so offline admins used to see entries "appear" that never reached the server. `AddEntryForm` now awaits the push ack: "Saving…" → "✓ saved" on ack, an amber "not confirmed — keep tab open, don't refresh" warning if no ack within 8s (offline writes queue in-tab and flush on reconnect; the promise never settles until then), red error on rejection. A `useConnectionStatus` hook (`src/hooks/useConnectionStatus.ts`, watches `.info/connected` with a 2.5s grace period) drives a sticky red offline banner shown in admin mode.
- **Player presence toggle** — `derby/disabledPlayers/{playerId}: true` marks a player as not at the derby. Admin mode shows every player with a HR in the leaders grid with tap-to-toggle IN/OUT badges; public mode hides disabled players entirely; all player dropdowns (add entry, edit entry, result) offer enabled players only. Entries referencing a since-disabled player still display via `fallbackLabel` on `PlayerCombobox`.
- **"Eligible Players" grid** shows ONLY players with ≥1 season HR (a homer is the ticket into the derby — 0-HR players never appear even if bet on). A "Sort by: Home Runs | Bets" chip toggle re-sorts the grid; the tile's big number is the active sort metric and the other metric shows as a small pill (`🔥 N BETS` in HR mode, `N HR` in bets mode). HR totals merge season `stats.hitting.hr` with live non-finalized games' `gameStats` (same pattern as StatsRoute), skip `isSub` players/at-bats, and filter out player records with no `name` (stale nodes exist in `/players` — sorting on `p.name` without the guard crashes the page).
- **Mobile-first** — most bettors open the page on a phone: CTA text uses `clamp()`, pot tiles use `auto-fit` grid, the public entries table has no forced min-width (admin table scrolls horizontally instead).

## Derby broadcast overlay (DerbyOverlayRoute.tsx + DerbyControllerRoute.tsx)
- **`/derby-overlay`** is an OBS browser source (1920×1080, transparent, read-only) for the derby broadcast; **`/derby-controller`** is the producer panel that drives it. This is separate from the `/derby` 50/50 public page, but shares its data root.
- **State lives at `/derby/broadcast`** (`DerbyBroadcastState`) — under `/derby` so it inherits that path's open write rule. The controller is gated by the same front-end password + `derbyAdmin` sessionStorage key as the /derby admin (constant duplicated in `DerbyControllerRoute.tsx`). Same accepted risk.
- **Shape**: `view` (`hidden | player | leaderboard | upNext`), `activeRound` (1|2|3, the round being hit), `leaderboardRound` (which round the leaderboard view shows — lets round 1 stay on screen while round 2 is underway), `featuredPlayerId`, `battingOrder` (playerId[]), `currentBatterIndex`, `scores/{playerId}` (`{r1?, r2?, r3?}`), `ticker` (bool), `timer` (`DerbyTimerState`).
- **A missing round score means "hasn't hit yet"; 0 is a real result** — never conflate them. Controller's "Done — next batter" converts a blank to a real 0 for the outgoing hitter.
- **Advancement is producer-confirmed, not score-derived** — `derby/broadcast/advancers` (`DerbyAdvancerLocks`: `{ r1?: playerId[], r2?: playerId[] }`) records who actually moved on OUT of a round. A tie for the last seat is settled by a swing-off that happens on the field, so the score cut is only ever a proposal: `cutInfo()` splits a round into `clinched` / `tied` / `spotsLeft` / `contested`, and `effectiveAdvancers()` returns the locked list when set, else the live cut. **All downstream consumers must go through `effectiveAdvancers` / `participantsForRound(…, locks)`** — the locked list governs the next round's field, the leaderboard cut line, and batting-order seeding. The controller's "Advancement" section drives it: round chips (R1→R2, R2→Final, following `activeRound`), a tick list of every hitter with their score, swing-off names called out in amber, then Confirm / Reset to score cut / Unlock. Editable at any time after the fact.
- **The left rail (`DerbyMiniBoardScene`) is the always-on board** — `derby/broadcast/miniBoard` (default **on**), rendered outside the `view` switch like the ticker and clock, and suppressed only while the full leaderboard takeover is up (same information, bigger). It lists **exactly the players who would move on as things stand**: normally the seat count, but everyone tied at the cut score stays on it and the depth is **open-ended** — 9 for a two-way tie at 8th, 10 for a three-way, and realistically more early in round 1 when a pile of hitters share a low cut score (7 clinched + 5 stuck on 2 HR = 12 alive for 8 seats). Never assume 8 or 9. Nobody alive may be dropped: any of them can win the swing-off, which is the whole reason the advancement lock exists. The hitter at the plate is pinned on the end while they climb (dimmed, `chasing: true`) and shimmers once they're in.
- **The left column is one dashboard, and `src/scenes/derby/layout.ts` owns its geometry** — turn clock → rail → hitter card → ticker, all flush at `DERBY_COL_X`/`DERBY_COL_W`. (The All-Star wordmark is *not* in this column — it watermarks the top right, opposite the league logo bug bottom-right.) The rail does not pick its own size: `derbyRailBand(clockVisible)` hands it the gap between the clock's bottom and the hitter card's top, and it absorbs depth by shrinking rows (46px → 22px floor; under 34px it goes compact — colour dot instead of a logo, no `TIE` pill, and the footer note collapses into the header's "N alive · N tied" chip). That fits **19 alive with the clock up, 24 without**; only past that does it cut the tail with a "+N more", and never the live hitter. It moves up into the clock's slot when the clock is toggled off. **If you move or resize the clock or the hitter card, update the constants in `layout.ts`** — the rail derives from them and will silently overlap otherwise.
- **The overlay does not trust `battingOrder` to be the current round's field** — it's producer-owned and can lag a round change (the controller shows an amber "this list isn't the {round} field" strip about exactly that). `DerbyOverlayRoute` derives `activeField` from `participantsForRound` and filters `orderRows` through it, because the overlay is what's on air. Without that filter a stale order put round 1 names — scoreless, reading TBD — straight into the round 2 ticker and Up Next board, while the left rail showed the right eight because it goes through `leaderboardForRound`. Anything new that renders from `battingOrder` must filter the same way.
- **The leaderboard is the advancement board** — rows are ranked by score (competition ranking, ties share) but *ordered* advancing-first, so the advancing set is always a prefix and one cut line suffices; the two orders only diverge after a swing-off, where the loser sits below the line still carrying the tied rank they earned. The line is drawn at `max(advancingCount, min(slots, rows))`, so it marks the N seats from the first pitch rather than creeping down as players hit. Round 3 has no cut (`ADVANCE_COUNT[3] === null`) — it just shows the three finalists and crowns rank 1 once all have hit.
- **Leaderboard layout is computed, not flowed** — rows are absolutely positioned from an index (`place()` in `DerbyLeaderboardScene`) and animate `x`/`y` with springs, so a hitter climbing the board glides to a known spot instead of being re-flowed. Row height adapts to the field size (62px down to a 40px floor) and past 16 hitters the board splits into two columns (`perCol = ceil(n/2)`, so a round-1 cut line stays in column one); the cut line consumes a slot in whichever column holds it. Geometry is arithmetic — if you change `ROWS_AVAIL_H`, `BASE_ROW_H`, or the padding, re-check that `panel ≤ 990px` at 30 rows.
- **The live hitter shimmers** — the leaderboard's `livePlayerId` is the current batter, passed only when `leaderboardRound === activeRound`. That row gets a breathing gold rim, a specular sweep, and an "On the clock" pill (CSS keyframes `derby-live-*` in `index.css`, transform/opacity only so they composite on the GPU). Score digits re-key on change so each home run pops.
- **`/derby-preview` is a dev-only route** — the derby boards against mock scores, no Firebase. `?n=` field size, `?scored=` how many have hit, `?round=`, `?tie=N` how many share the cut score (the board runs 7 + N deep, so `tie=5` is 12 and `tie=13` is 20 — `scored` stretches itself to make the tie possible), `?locked` to confirm the field, `?clock=0` to drop the turn clock, `?big` for the takeover instead of the rail, `?champion` for the winner graphic (with `?bets=0|1|2|3` for no winner / one winner / a two-way split / a three-way split), `?odds` for the 50/50 odds board. `?odds` runs the **real** `useDerbyOdds` hook against mock objects (the hook takes its state as arguments, not from Firebase), so it previews the chunked simulation path and not just the pure model — but on its OWN realistic mock board, because the `n`/`scored`/`tie` scores are spaced 40/38/36 to force distinct ranks and a field averaging 38 a round projects a winning total near 100. The odds board and the rail therefore disagree about who's leading on purpose. The default view renders the whole left column (clock + rail + hitter card) so the dashboard stack can be checked as one. Use it to eyeball ties, cut lines, and the live row without waiting for derby night.
- **Bracket rules in `src/derby/logic.ts`** (pure, no Firebase/React): round 1 = all eligible; top 8 advance out of round 1, top 3 out of round 2. **Ties for the last spot all sit above the line until the producer settles them** (`advancersFromRound` takes everyone ≥ the Nth score; `effectiveAdvancers` then defers to the locked list). Only players with a recorded score can advance, so mid-round the cut line is a live preview. `leaderboardForRound` returns rows ranked by score with yet-to-hit rows dimmed at the bottom, ordered advancing-first. Covered by `src/derby/__tests__/logic.test.ts` — ties, locks, and round chaining all have cases; extend it rather than eyeballing bracket changes.
- **Eligible pool = `useDerbyContestants`** — same rule as the 50/50 page: non-sub players with ≥1 season HR (finalized stats + live non-finalized games) minus `derby/disabledPlayers`. Both derby broadcast pages and any future consumer should use this hook, not re-derive it.
- **Batting order auto-fills** — when the controller loads and `battingOrder` is empty, it seeds itself with ALL hitters of the active round (no hand-adding); the producer only dismisses (✕) or drags. Guarded by a per-session ref so deliberately emptying the list doesn't refill it. "Load order" re-seeds explicitly (with confirm).
- **Seeding order — direction flips after round 1** (`seedOrderForRound` in `derby/logic.ts`, tested): **rounds 2 and 3 hit fewest previous-round HR FIRST**, so the leaders bat last and the round builds to them — that's how the derby is actually run. Round 1 has no derby score yet, so it seeds by season HR *descending* and the big bats open. Ties break on season HR in the same direction, then name. The controller states the rule above the order list and prints each row's seed number (`· 9 R1`), because a list of names alone gives no clue which direction it used.
- **Switching `activeRound` re-seeds the batting order** — `setActiveRound` writes the new round's field in that round's order in the same `update()`, but only when the field actually changed (`sameSet`), so bouncing between rounds doesn't discard hand-dragged order. Without this the previous round's whole order stayed on screen. A mismatch between the stored order and the round's participants also shows an amber "This list isn't the {round} field" strip with a one-tap fix. Producer then **drags rows to reorder** (framer-motion `Reorder`, whole-row drag, commit to Firebase on drop with `currentBatterIndex` following the current batter's id). Because drag owns the row click gesture, selecting the current batter is double-click or the per-row ▶ button — do not reattach tap-to-select to the row.
- **Ticker is independent of `view`** — `derby/broadcast/ticker` (boolean) is a separate toggle in the controller's "Broadcast view" section, so the bottom crawl can run under any scene *or* over a clean camera shot with `view: 'hidden'`. The league logo bug lifts to `bottom: 88` while the ticker is up.
- **The ticker cycles rounds as ESPN-style topic blocks** — `DerbyTickerScene` takes `DerbyTickerSegment[]`: one per round, **current round first then every round already hit** (live round in batting order with the hitter at the plate flagged `AT BAT`; finished rounds ranked, since by then they're results). Each segment is `[label][its hitters]`. A segment's label **docks** at the left edge while its scores crawl past, and the next segment's label travels in from the right and slides *over* the docked one to take the dock — so the round on screen is always named. Scores are clipped at the label's right edge (the rows live in a container inset by `labelW`), so they vanish behind the label rather than sliding past it. All labels are forced to one width, which makes the hand-off pixel-exact and gives the clip a single boundary.
- **Ticker geometry, and the one place rAF is allowed** — a label holds still while the track keeps moving, which is a clamp against the track position, not a fixed curve, so it cannot be a CSS keyframe; splitting it into per-label animations would drift out of phase and glitch the hand-off every cycle. One rAF loop therefore drives everything from a single elapsed-time origin, writing **only** `transform` per frame (`zIndex`/`visibility` are written on change). Do not add a layout-triggering write to that loop. The docked window is half-open — `mod(scroll - start, total) < span` — so spans partition the loop and exactly one label is docked on every frame; the intuitive `u > total - span` leaves the dock empty for one frame at each hand-off. A trailing pad keeps the track longer than the bar so one label element per segment is always enough. Re-measures on `document.fonts.ready`, and score cells have a fixed width so a home run landing mid-crawl can't reflow the track under the maths.
- **Turn clock — 90s per hitter + one 30s timeout** — `derby/broadcast/timer` (`DerbyTimerState`), drawn by `DerbyTurnClock` top-left under the All-Star lockup (the one corner no derby scene uses) and, like the ticker, **independent of `view`** via its own `visible` toggle. Elapsed time is never counted in Firebase: the state holds `phase` (`main | timeout`), `running`, `startedAt`, the two `remainingMs` values and the two durations, and every device derives the live number from `startedAt` (`derbyTimerRemainingMs`). Taking the timeout freezes the turn clock at `remainingMs` and runs the 30s; when it expires **the turn clock auto-resumes** — no producer input. `timeoutUsed` is one per hitter per round and clears on reset.
- **The clock resets itself on every batter change** — `timerResetPatch(playerId)` returns multi-path `timer/*` keys that ride in the *same* `update()` as the batter/round change (next batter, prev, ▶ select, load order, round switch), so the clock and the hitter can never drift apart. `timer.playerId` stamps whose turn it is; the controller flags it when it doesn't match the current batter.
- **Clock transitions are controller writes, but the overlay derives them too** — the overlay is read-only, so the controller schedules one `setTimeout` per running segment (same pattern as the game controller's stat auto-dismiss) to write the timeout→hitting rollover and the final stop. Because a backgrounded producer tab gets its timers throttled, `resolveDerbyTimer(timer, now)` (pure, in `derby/logic.ts`) rolls an expired timeout into the resumed turn clock for *display*, anchored at `startedAt + timeoutRemainingMs` so the derived and written versions agree to the millisecond. Controller write helpers act on the resolved state and always write `phase` explicitly — otherwise stopping a rolled-over clock would re-commit the stale `timeout` phase.
- **Money ball — the one pitch after 0:00, worth 3** — when the turn clock expires the hitter gets a final pitch; a homer off it counts `DERBY_MONEY_BALL_HR` (3). The controller's gold `💰 MONEY BALL +3` button (in "Now batting", under +1 HOME RUN) unlocks *only* while `timerExpired && timer.moneyBallAt == null`, and writes the +3 **and** `timer/moneyBallAt` in ONE atomic `update()` — the overlay must see both in a single snapshot. An `↺ Undo` appears afterwards (−3, clears the timestamp) for a misfire on air. `moneyBallAt` is per-turn state on the timer, so `timerResetPatch` clears it for the next hitter.
- **`moneyBallAt` doubles as the animation trigger** — `DerbyMoneyBallScene` (`DerbyMoneyBall`, keyed by the timestamp in `DerbyOverlayRoute` at `zIndex: 50`) plays a full-screen takeover for `MONEY_BALL_ANIM_MS` (3.2s): gold wash, shockwaves, a gold wiffle ball flying in, "MONEY BALL" slam, a `+3 HOME RUNS` plate and falling `$`. The gate starts already-finished when `at` is stale, so a reloaded overlay never replays an old one. Because the +3 arrives in the same snapshot, `DerbyPlayerScene` takes `moneyBallAt` and **skips its usual home run burst** on that bump — the two celebrations must never fire together. Spreads are hand-authored constant arrays: no `Math.random` in render. On air the clock card reads gold `FINAL PITCH / MONEY BALL IN PLAY` between 0:00 and the swing, then `MONEY BALL +3`.
- **Celebration graphics are CSS, not JS — this is a frame-rate rule, not a style preference.** The money ball and the home run burst both animate through the shared `derby-mb-*` / `derby-hr-*` keyframes in `index.css` (`.derby-mb-anim` = `animation-fill-mode: both` + `backface-visibility: hidden`); per-element direction, spin and stagger come in as `--mb-x` / `--mb-y` / `--mb-spin` / `--mb-drift` / `--mb-ring-to` custom properties, so they run on the compositor and cost the main thread nothing after the first frame. The first cut used framer-motion with `filter: drop-shadow` on the flying ball, a glow `box-shadow` per particle, three stacked `text-shadow`s under a scaling stroked headline and ~28 particles — it dropped frames in OBS *and* in Chrome on an M1. **Never animate `filter`, `box-shadow`, `width`/`height` or anything else that re-rasterises here, and keep the particle count in the teens.** Framer is still fine for one-shot entrances of a single card.
- **Composited is not the same as free — four rules the money ball had to learn.** (1) **Never `scale` text or vector content.** Each new scale factor re-rasterises the glyph paths, and a stroked 150px headline is the most expensive thing on the canvas to raster; the slam, the plate and the ball move with `translate`/`rotate`/`opacity` only, and their static tilt lives on a non-animating wrapper. `scale` is reserved for the shockwave rings and the solid-colour sparks, which raster trivially. (2) **No wrapper-level opacity fade** over a subtree of composited children — it forces a full-screen render surface every frame; each piece fades itself instead. (3) **No `will-change`.** Chrome composites a transform/opacity animation the moment it starts; `will-change` instead promotes and rasterises every layer at mount, which is one big hitch exactly as the graphic appears. (4) **Big soft gradients are rasterised small and blown up with a static `scale`** — the impact wash is a 700×700 element at `scale(2.4)`, a fifth of the pixels of a frame-filling gradient and visually identical because it is a soft radial.
- **The turn clock re-renders ~10×/s, so nothing inside it may build an animation per render** — its depleting bar is a `scaleX` transform with a CSS transition (a `width` animation would force layout on every tick for the whole 90 seconds), and the last-10s pulse is the `.derby-clock-pulse` class (opacity — pulsing `scale` on 78px stroked text re-rasterises the glyphs every frame).
- **`/derby-preview?money=1`** loops the money-ball graphic (clock forced to 0:00) so it can be judged without Firebase or a live derby; add **`&fps`** for a live frame-rate readout (avg over the last second + worst single frame; over ~20ms is a visible hitch). Judge animation cost there, on the machine that will actually run the broadcast — a backgrounded tab throttles rAF to nothing, so headless/automated measurement of these graphics is meaningless.
- **Home run burst** — `DerbyPlayerScene` watches the active round's score and fires a "HOME RUN!" slam + shockwave + particle burst whenever it increases (`activeScore > (prev ?? 0)`: no burst on mount, on −1 corrections, or when "next batter" locks a blank in as 0). Overlay stays read-only — the animation is derived purely from score changes.
- **The champion graphic draws `derby/result`, not the derby scores** — so selecting the Champion view before anyone is declared puts *nothing* on air. That used to be silent in both directions: blank overlay, no word in the controller. The Broadcast view section now warns when `view === 'winner'` with no posted result and opens the Champion section (whose `open` state the panel owns for that reason), and if nobody has reached the final that section says what's missing rather than just that something is. The warning is gated on `useDerbyBets().loading` — which waits for *both* its paths, not just whichever snapshot lands first — so it can't flash on a refresh of a derby that does have a champion.
- **Champion graphic + settling the 50/50** — `view: 'winner'` draws `DerbyWinnerScene`: crown, laurels, the champion's name, their 3-round total and per-round breakdown, and the settled bet with payouts. It's the one derby graphic that is **held** on air (the winner gets interviewed under it), so its entrance settles into a pose rather than clearing itself, and only the laurels and confetti keep looping — same CSS-only rules as the money ball (`derby-win-*` in `index.css`). The rail, ticker and turn clock hide themselves under it.
- **Each hitter has a pitcher — `derby/broadcast/pitchers/{batterId}`, keyed by the BATTER.** A derby hitter brings their own pitcher and keeps them all night, so it's per hitter, not per hitter-per-round. Stored as a **plain name, not a playerId**: whoever is grooving them is usually not in the derby field and often not on a roster at all. Editable in two places because both are the natural moment — the current hitter's field in "Now batting", and a compact one on every row of the batting order for pre-filling. Every field shares one `<datalist>` (`PITCHER_LIST_ID`) built from the distinct names already entered tonight, since the same three or four people throw to the whole field. Blank clears the key rather than storing `""`, so the overlay's check stays a truthy test. `DerbyPlayerScene` shows it as a `PITCHING <name>` item on the hitter card's stat line (which wraps, since the name is arbitrary length). The controller's "Reset the derby for a fresh run" clears `pitchers` along with the scores; the `/derby` "Archive & reset" gets it for free by archiving and nulling the whole `derby/broadcast` subtree.
- **`PitcherInput` re-seeds by REMOUNTING on the caller's `key`, not by syncing in an effect** — the key carries the stored value, so an external write remounts it while typing leaves it alone. `ScoreInput` next to it does use the effect-sync pattern and carries a lint error for it; don't copy that one. It also stops `pointerdown` propagating, because `Reorder.Item` owns the row's drag gesture and would otherwise start a drag instead of focusing the field.
- **The 50/50 odds board (`DerbyOddsScene`) answers "who's most likely to take the pot", which is NOT "who's leading"** — an entry only cashes if it named the hitter who actually wins *and* called that hitter's 3-round total closest, so the top of this board routinely disagrees with the top of the leaderboard. Right-hand panel, top five entries. **Each row is ONE line — `BETTOR on HITTER call` — with both names at the same size.** It was a two-liner with the pick in 11px underneath; that vanishes on a stream, which is where this is actually watched. Rules that follow: the bettor is bright white and the hitter dimmed, the hitter carries the team badge, the call is gold, and a `BETTOR · BACKING · CALL` header sits above the rows. Most of the betting pool is itself in the derby, so **without those cues the leading name reads as a hitter and the board looks like it's calling the wrong person to win** — don't drop them, and don't shrink the hitter to a caption again. Nothing on the row goes below ~11px; the per-row "hitter %" was cut rather than kept tiny (the footer still carries the favourite's chance). Only the bettor name ellipsises — the hitter is a last name and rarely needs to. footer carries the model's projected champion + winning total and the odds nobody called it (whole pot to charity). Suppressed under the leaderboard, Up Next and the champion graphic (all three own the right-hand side or the whole screen) — everything else it can sit over.
- **The odds are a Monte Carlo of the rest of the derby, in `src/derby/odds.ts`** (pure, no Firebase/React, tested in `__tests__/odds.test.ts`). The bet couples two random things — champion identity and champion total — through a bracket with ties, producer locks and a money ball, so there is no closed form worth writing. Each trial: draw every live hitter a rate, simulate their unfinished turns, take the cuts (**an unsettled tie for the last seat is a coin flip — that's the swing-off**), crown a champion, then settle the 50/50 against that ending exactly as `derbyBetWinners` would. Counting how often each entry holds the winning ticket gives `winProb`; ties split, so `expectedShare` (not `winProb`) is what sums to 1 with `charityProb`.
- **The sim starts from `model.liveField` — the board's field — NOT from round 1, and this is a correctness rule, not an optimisation.** `liveField` is `participantsForRound(…, activeRound, locks)`, the same list the leaderboard and rail draw, so **a hitter who did not advance is absent and reads 0% by construction**. Replaying the bracket from round 1 instead let the sim re-derive old cuts and deal eliminated players back in: with round 1 left incomplete (blanks scored as 0) and only five hitters above zero, the top-8 cut had three seats spare and **players who never took a swing were coming out at 3.7% to win the derby**. Rounds before `activeRound` are history — their scores are read off the board for the champion's three-round total and never simulated. The one thing still genuinely open is an unsettled tie for the last seat, so the incoming field is trimmed to the seat count per trial, which flips that swing-off; a locked round short-circuits to the locked list.
- **Rates are fitted two-level Gamma-Poisson, and tonight's hitting beats the season line fast.** A hitter's prior is `leagueRoundMean × weight`, where `weight` shrinks season HR hard (`(hr + 6) / (avgHr + 6)` — derby pitching is grooved and a wiffle season is a tiny sample, so the best bat opens at ~2.5× the worst, not 10×). `leagueRoundMean` is itself re-estimated from tonight's scores divided by the weight of whoever produced them, so a cold round drags every projection down. The player prior is worth only `PLAYER_PRIOR_ROUNDS = 1.5` rounds, so one completed round moves a hitter most of the way to what they just did. **Every constant in that file is a prior that live data washes out** — retune them there, not at the call sites.
- **Two things the model must keep doing.** Each round's rate is multiplied by a mean-1 `Gamma(6, 6)` draw (`ROUND_DISPERSION`) because derby rounds are far streakier than Poisson; without it the leader's win probability comes out absurdly high. And the turn in progress is **pro-rated by the clock** — 6 HR with a third of the turn gone is a monster pace, 6 with the turn nearly over is merely good — with the money ball added back at its expected value only when `moneyBallTaken` is false. Recorded round totals already have money balls baked in and nothing stores whether a past one went out, so the money ball is only ever split back out for the live turn.
- **Two ways on screen, and the cycle is HIDDEN-FIRST** — `derby/broadcast/odds` (`DerbyOddsState`: `enabled`, `mode`, `startedAt`, `intervalMs`, `durationMs`), default `enabled: true, mode: 'timer'`, 60s cycle / 15s up. `mode: 'always'` parks the board on screen for the whole derby; the controller's **"Keep it up: YES/NO"** is the switch, and NO drops to the cycle rather than banishing the board (`enabled: false` is the real off). The cycle runs **away for `interval - duration` then up for `duration`** — hidden-first is the point: the producer reaches for this by taking the board *down*, and a visible-first cycle would slam it straight back up, so toggling off stamps `startedAt = now` and the away stretch starts there. **That schedule is DERIVED**: the overlay can't write, so nothing marks the board visible — `derbyOddsWindow(odds, now)` works it out from `startedAt` the same way the turn clock derives its remaining time, and controller and overlay agree without a round trip. "Show now" writes `derbyOddsShowNowAt` (wind `startedAt` back past the away stretch), and a stamp in the *future* — producer's clock ahead of the overlay's — reads as the top of the away stretch rather than a negative phase wrapping to somewhere random.
- **Two things the board needs because it can sit still for a long stretch.** The overlay hides it while `derby/entries` is empty — otherwise an "on" default puts a "no entries yet" panel on air before anyone has Venmo'd in. And rows carry framer `layout` inside a `popLayout` `AnimatePresence`: while the board is up, the moment worth animating is a bettor **changing places**, so a row glides to its new slot rather than the list re-flowing under the viewer. Entrance stagger is deliberately off the update path — a per-row `delay` would make every swap look laggy. The panel is 440 wide at `top: 108`, which clears the All-Star wordmark watermark sharing the top-right corner.
- **`useDerbyOdds` is keyed on `derbyOddsSignature`, and the run is sliced** — the signature quantises the turn clock to **eighths** so a clock ticking ten times a second can't drag a Monte Carlo along with it, and hashes to the RNG seed so the numbers are identical on controller and overlay and don't twitch between re-renders. The 12k trials are run in 750-trial slices yielded through a **MessageChannel, not `setTimeout`** — a backgrounded tab clamps timers to ~1/s, which stretched a 16-slice run to a quarter of a minute on the producer's control tab. The previous result stays on screen while a new one computes, so the board never blanks mid-shot.
- **The champion is whoever WINS THE FINAL ROUND — not whoever hit the most home runs overall.** A hitter can be quiet through rounds 1 and 2, win the final, and be the champion on a smaller three-round total than somebody they beat; the 50/50 then pays on *their* total. Worked example, and it is in the tests: A goes 5 / 5 / 16 for 26 and wins the final; B goes 15 / 15 / 3 for 33 and loses it. A is champion, and the entry closest to **26** takes the pot — a bet that nailed B's 33 gets nothing, and so does a bet of 33 on A. `leaderboardForRound(…, 3, …)` ranks the final by its own round score, `derbyTotal` supplies the three-round number, and `ChampionSection` pre-fills from exactly those two. Never rank the final by `total`.
- **`derbyBetWinners` in `derby/logic.ts` is the single definition of who wins the bet** (pure + tested; `/derby` and the champion graphic both call it — do not write a second copy). An entry is eligible only if it picked the player who actually won; among those, the smallest `|guess − winner's 3-round total|` takes it, **direction irrelevant** — on a 29 total, 28 and 30 are equally close and both win. Any number can tie (either side of the number, or several on the same number) and they split evenly via `derbyPayout` (half to charity, half shared; charity gets the odd dollar). Nobody eligible → the whole pot goes to charity.
- **Two different resets — never conflate them.** The derby has *practice* data (home run scores, which are fake until derby night) and *real* data (the 50/50 bets, which are money already sent over Venmo).
  - **Controller → "Reset" section → `↺ Reset derby scores & champion`** — the practice wipe. Clears `derby/broadcast/scores`, `advancers`, the batting order/round/timer and `derby/result`, then re-seeds the round-1 order so it's ready to run again. **It must never touch `derby/entries` or `derby/disabledPlayers`** — the confirm dialog states what goes and what stays, and the section prints both counts. Nothing is archived.
  - **`/derby` → Season tools → "Archive this derby & reset"** — the real end-of-season rollover. Freezes bets *and* scores into `derby/archive/{year}` before clearing. This is the only path that may delete entries.
- **Resetting the champion** — the Champion section is **always mounted**, whatever round is selected, and its title reads "Champion — result posted" when one is live; a posted result shows a banner with `↺ Reset champion` (removes `derby/result` here, on the overlay and on /derby; derby scores untouched) plus a Show button. Gating that section on `activeRound === 3` stranded the reset after a test run. Resetting also drops the overlay off `view: 'winner'`, and the overlay's takeover suppressions key off `championUp` (view is `winner` **and** a winner exists) — otherwise clearing a result mid-graphic leaves a blank screen with the rail, ticker and clock all stood down.
- **Declaring the champion posts to `/derby` too** — the controller's "Champion" section pre-fills the winner from the final-round leader and the total from `derbyTotal`, previews exactly who wins the bet and for how much *before* it goes on air, then writes `derby/result` and cuts the overlay to the graphic in one action. The graphic reads `derby/result`, so the broadcast and the public page can never name different winners. **On air every entry counts** — the entry IS the Venmo payment — while `/derby` still gates on its `paid` flag, so the controller warns when an entry is left unticked (the only way the two can disagree).

## All-Star Game (2026 Brookside All-Star Weekend)
**Full product doc: `ALLSTAR.md` — read it before touching all-star code. The hard rule: all-star at-bats NEVER reach `players/{id}/stats`.**
- Exhibition detection is data-driven: `isExhibitionGame(g, teams)` checks the game record's `isExhibition` flag (stamped at creation), then either team's `isExhibition` flag, then the legacy 2026 ids. Annual rollover is a documented runbook in ALLSTAR.md (one config edit + logo regen for the game; one admin button — derby "Season tools → Archive & reset" — for the derby, which snapshots to `derby/archive/{year}`).
- The All-Star Weekend lockup is **text, not an image** — `components/AllStarWordmark.tsx`. It watermarks the derby overlay's top right always, and the game overlay automatically whenever an exhibition matchup is on the scorebug.
- **Team Rist (red, `team_rist`) vs Team Hiller (blue, `team_hiller`)** — exhibition teams of players drafted from across the league. NOT separate routes: the regular `/controller`, `/overlay`, and `/scorekeeper` run the all-star game once the teams are seeded and picked as home/away, exactly like a normal matchup.
- **Seeding is an admin button** — `/config` has an "All-Star Game" section: one click writes `teams/team_rist` + `teams/team_hiller` and `config/allstar/rosters/{teamId}` (playerId[]) from the constants in `src/allstar.ts` (`ALLSTAR_SEED_TEAMS` / `ALLSTAR_SEED_ROSTERS`). Roster changes = edit `src/allstar.ts`, redeploy, hit "Re-seed from code". "Remove" deletes both teams and `config/allstar`. Rosters live under `/config` (admin-writable) specifically so no database-rules change was needed.
- **Players keep their league `teamId`** — membership comes from the roster mapping. ALL player-by-team filtering must go through `src/allstar.ts` helpers: `playerOnTeam(id, player, teamId, rosters)` (replaces `p.teamId === teamId`), `effectiveGameTeamId` (which side of this game a player is on — used for stat-overlay/matchup accent colors), `buildPlayerTeamMap` (roster-aware map for `computeLineupPosition`). `useAllstarRosters()` (hook, `config/allstar/rosters`) returns null until seeded, making every helper fall back to plain league-team matching — zero regular-season impact.
- **Roster-aware call sites** — ControllerRoute (batter/pitcher dropdowns, `selectPitcher` home/away detection), Scoreboard (notch visibility), StatCardScene, MatchupScene + StatOverlay (accent team resolution), ScorekeeperRoute (LineupBuilder, batter/pitcher options, sub-pitcher roster list, live-stats side split, AtBatEditModal options, both `computeLineupPosition` team maps), SummaryRoute (box-score side split). GameEditorRoute was NOT made roster-aware (admin edit tool; known limitation).
- **Exhibition games never touch season stats** — `isExhibitionGame(g)` (either team is an all-star team) guards: Finalize is replaced with an "exhibition" notice in ControllerRoute and hard-blocked in ScorekeeperRoute's `finalizeGame`; live season-stat merges skip exhibition games in StatsRoute, DerbyRoute, and `useDerbyContestants`. Standings/results only count finalized games, so exhibitions never appear there.
- **`allstarLineups` scene** (`⭐ Lineups` button) — full-screen board: All-Star Weekend lockup on top, both batting orders side by side with season AVG/HR/RBI and each player's league-team logo. Order preference: scorekeeper lineup (if a game is linked) → drafted roster order → team filter.
- **Logos are static SVGs in `public/logos/`** — `team-rist.svg` and `team-hiller.svg` only; the weekend lockup is no longer an SVG. Served same-origin (no Firebase Storage upload); `logoUrl` uses absolute paths like `/logos/team-rist.svg`.
- **The wordmark is two lines of live text, tracked to equal width** — `AllStarWordmark.tsx` stacks ALLSTAR (blue) over WEEKEND (red), nothing between them. Both lines are tracked so their **ink** widths match exactly and the stack squares off: at zero tracking Barlow Condensed **900** sets them 3.3100em and 3.5430em wide, and the shorter word takes the extra. Those constants are weight-specific (the 700 face is much narrower) — re-measure with canvas `TextMetrics` if the words or the weight change, don't nudge by eye.
- **Two CSS gotchas are already compensated for; don't "simplify" them away.** (1) `letter-spacing` is applied after the LAST glyph too, so each line carries a matching negative `margin-right` — without it the trailing space shoves the ink off centre by `ls/2`. (2) With `line-height: 1` the line box is 1em but the font's box is 1.20em (ascent 1.00 + descent 0.20), so the baseline sits 0.90em down: **0.20em of slack above the caps and only 0.10em below the baseline**. The two boxes therefore already hold the lines 0.30em apart on their own, so `LINE_GAP_EM` works down from that (it goes slightly negative) rather than up from zero. The line wrapper also sets `font-size` explicitly so its strut matches the inline-block and the box is exactly 1em tall.
- **The wordmark is a bare watermark, not a card** — `top: 24, right: 32, opacity: 0.7`, deliberately mirroring the league logo bug at `bottom: 24, right: 32`. A card treatment in the left column was tried and rejected: the column is the busy side and a fourth panel just crowded it. Nothing else uses the top right — the leaderboard takeover ends around x=1336, the mark starts at 1755. **The `star` prop** puts a gold star behind the type, centred on the INK rather than the box (the box carries the font's leading, which would sit it ~2px high). **There is no text outline** — the type is plain bold condensed like the derby name rows — so the star stays faint (0.3) and a soft drop shadow is all that separates them; pushing the star up muddies the type immediately. That also forces the colours: the wordmark uses **on-dark tints** (`#5b9df9` / `#f56e6e`), not the raw team colours, which are dark navy and maroon and unreadable as unoutlined type over video. Those tints are **not derived** from `ALLSTAR_SEED_TEAMS`, so a team colour change has to update both — flagged in ALLSTAR.md's runbook.

## Fonts
Always use `fontFamily: 'var(--font-score)'` for scoreboard/stat numbers and `var(--font-ui)` for prose/labels. Do not use Tailwind's `font-sans` — it won't load the right font.
